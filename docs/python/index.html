🧭 为什么这样设计 · 名字不是盒子

「变量是个盒子，装值进去」是最常见的比喻，也是最容易骗人的比喻。在 Python 里，名字（name）和对象（object）是彻底分开的两样东西：

  • x = 100 不是把 100 塞进盒子，而是把名字 x 绑定到整数对象 100 上。
  • 绑定之后一个对象可以有多个名字：a = b = [] 里 a 和 b 指向同一个列表对象。
  • 重新赋值只是换一个绑定：x = 100 之后再 x = "hi"，那个整数对象并没有被改坏（没人引用它时才被回收）。

为什么非要这么设计？因为这样「传参」就完全没有魔法了：把对象传给函数，传的其实只是名字；函数体内换个名字，不影响调用方那边。C 语言里变量是存储位置，名字只是那块内存的标签；Python 里名字是字典里的一个 key，值是对象引用——这就是「一切皆对象」的落地方式。

🎯

代价：初学者容易以为赋值就是复制，于是写出 b = a 之后就以为两者互不相干。后面陷阱清单第 1 条就是这个坑。

⚙️ 底层机制 · 名字是字典里的一个 key
  • 名字存在两本字典里：函数自己的局部变量表 f_locals，以及模块的全局字典 f_globals。x = 1 编译后是 STORE_FAST / STORE_NAME / STORE_GLOBAL，本质就是往字典里塞一个 key。
  • 读变量对应 LOAD_FAST / LOAD_NAME / LOAD_GLOBAL。编译器在编译期做符号分析，因此能提前判定某个名字是局部还是全局——下面陷阱第 5 条的 UnboundLocalError 就是这么来的。
  • 局部变量随函数栈帧一起销毁；全局名字活在模块字典里，直到模块被卸载。
  • CPython 还预建并复用了一组小整数对象（-5 到 256），所以同一个程序里写两遍 256，拿到的其实是同一个对象。

以上是 CPython 的实现细节，可能随版本变化；语言规范只保证「名字绑定到对象」这一层语义。

⚠️ 陷阱清单
python陷阱1 赋值不是拷贝
a = [1, 2]
b = a            # 绑定，不是拷贝
b.append(3)
print(a)         # 输出: [1, 2, 3]

原因：赋值只做绑定，a 和 b 指向同一个 list 对象，改一个另一个也变。

python陷阱2 is 与 等于
x = []
y = []
print(x == y)    # 输出: True  ← 内容一样
print(x is y)    # 输出: False  ← 但是两个不同的列表对象

原因：== 比的是值，is 比的是身份（id()）。两个空列表内容相等，但不是同一个对象。

python陷阱3 小整数驻留
a = 256
b = 256
print(a is b)        # 输出: True  ← 落在小整数缓存里
c = int("257")
d = int("257")
print(c is d)        # 输出: False  ← 257 超出缓存范围

原因：CPython 复用 -5 ~ 256 的整数对象，所以用 is 比较数字大小毫无意义。

python陷阱4 循环变量泄漏
for i in range(3):
    pass
print(i)             # 输出: 2

原因：Python 只有函数级作用域、没有块级作用域，for 的循环变量循环结束后依然存在（这里是最后一次迭代的值）。

python陷阱5 局部变量未赋值
def f():
    print(n)        # 报错
    n = 1

try:
    f()
except UnboundLocalError as e:
    print(type(e).__name__)   # 输出: UnboundLocalError

原因：编译器看到 n = 1 就认定 n 是局部变量，把上面的 print(n) 编译成「读一个还没赋值的局部变量」，于是抛 UnboundLocalError 而非 NameError。

🚀 进阶用法 · __main__ 守卫
pythonmain 守卫
def main():
    print("真正的入口在这里")

if __name__ == "__main__":
    main()

直接 python demo.py 运行时，模块里的 __name__ 是 "__main__"；被 import demo 引用时它是 "demo"，于是 main() 不会自动跑。这样同一个文件既能当脚本执行，又能当模块被复用，不会一 import 就打印一堆东西。

python交换与解包
a, b = 1, 2
a, b = b, a          # 交换，不用临时变量
head, *rest = [1, 2, 3, 4]

解包和交换都走的是「打包 → 解包」这一套字节码。交换两个变量在模块层会编译成一条栈交换指令（3.10 及以前叫 ROT_TWO，3.11 改名叫 SWAP），而在函数体内编译器常常直接重排两个 STORE，连交换指令都不发——总之零成本。（CPython 实现细节，可能随版本变化）

str 和 bytes 是两种类型，不一样：len("中") 是 1（按字符），len("中".encode()) 是 3（按字节）。str 用 str 方法，bytes 用自己的那套（decode() / hex()…），方法名几乎不通用。需要频繁改动的缓冲区用 bytearray，它是可变的。

🧭 为什么这样设计 · 整数无限、浮点守规矩
  • int 为什么是任意精度？Python 想让「整数多大都行」，不用像 C 那样分 short / int / long，代价是大整数慢。
  • float 为什么还是 IEEE 754 双精度？要跟 C、Java、JS 互通，浮点标准必须统一。代价是 0.1 这类十进制小数没法精确表示，于是有了 Decimal 和 Fraction。
  • bool 为什么继承 int？历史包袱：True / False 本就是整数 1 和 0，继承下来能当计数用；副作用是 True == 1。
  • f-string 为什么取代 % 格式化？% 要背一整张占位符表（%s %d %r %f %x…）。f-string（PEP 498，3.6 引入）用 {} 包住完整的 Python 表达式，规格直接复用 format()，% 只剩兼容老代码的意义。
⚙️ 底层机制 · int、float、bool 各自长什么样
  • int：CPython 里是 PyLong，按 30 位一段（64 位平台）分段存储；内部用符号-绝对值表示（ob_size 存符号，ob_digit 存绝对值），位运算时才按补码语义处理。2 ** 1000 随手就能算。
  • float：就是 C 的 double，IEEE 754 binary64：1 位符号 + 11 位指数 + 52 位尾数。0.1 的二进制展开是无限循环的，只能取最接近的近似值。
  • bool：是独立于 int 的一个类型（CPython 里的 PyBool_Type，继承自 PyLong_Type），只是只有 True / False 两个单例值。所以 type(True) is type(1) 是 False，可 True + True == 2。
  • Decimal / Fraction：Decimal 用十进制位存，默认 28 位有效数字；Fraction 存最简的「分子 / 分母」整数对，自动约分。

以上是 CPython 的实现细节，可能随版本变化。语言规范只保证 int 任意精度、float 是双精度近似值、bool 继承 int。

🧭 为什么这样设计 · 返回操作数，而不是返回 True/False
  • x and y 的语义被定义成「x 是假就返回 x，否则返回 y」，x or y 是「x 是真就返回 x，否则返回 y」。这不是随手设计的，而是为了让「保护性取值」能写在一行里：cfg and cfg["timeout"]，中间对象不会被 bool 化丢掉。
  • Guido 自己的说法是：x and y 等价于「返回第一个假值，否则返回最后一个值」。所以 and 天然偏向返回假值，or 天然偏向返回真值。
  • 为什么没有 ++ / --？因为 x += 1 本身就是表达式，能塞进任何需要值的地方（参数、返回值、推导式），一条就够；而 C 的 x++ 是语句、结果不可用，没有单独存在的必要。背后走的是 __iadd__ 协议。
  • 为什么单独给 //？5 / 2 得 2.5，但「分几页」「每组几个」这类问题要的是整数答案。// 明确表示整除，避免把 0.5 这种小数带进后面的计算里。
⚙️ 底层机制 · 表达式怎么被编译
  • CPython 先用符号表 + 优先级表把表达式解析成一棵树，再编译成栈式求值的字节码：常量入栈、运算符出栈弹两个再压一个。
  • 短路求值对应「条件跳转 + 把操作数留在栈上」这一组字节码：3.11 及以前是 JUMP_IF_FALSE_OR_POP / JUMP_IF_TRUE_OR_POP，名字里的 OR_POP 就是「弹出并保留操作数」；3.12 起这两条指令已被移除、改用别的组合。走短路分支时右操作数压根没被求值。
  • ** 是右结合的：2 ** 3 ** 2 等于 2 ** (3 ** 2)。数学上这么定是因为指数塔本来就要从右往左算；其余二元运算符一律左结合。
  • 位运算作用在「无限位补码」上，负数按符号扩展，所以 ~n == -(n + 1) 对任何整数都成立。
  • 复合赋值 a += b：可变对象上走 __iadd__（原地改），不可变对象上等价于 a = a + b（新建对象再重新绑定）。

以上是 CPython 的实现细节，可能随版本变化；语言规范保证的是运算结果和求值顺序。

🧭 为什么这样设计 · 缩进即代码块
  • 为什么用缩进而不用花括号？省掉一行括号和分号，视觉上更干净；代价是缩进写错就是语法错误。更重要的是，块边界是确定的，所以 Python 从来没有 C 语言那个「悬挂 else」难题——else 一定属于最近的、还没被匹配上的那个 if。
  • 冒号后可以跟一条语句（if x: print(1) 合法），但只能一条；要多行就必须换行并缩进。
  • 为什么长期没有 switch？C 的 switch 只会拿值跟一堆常量比「相等」。而 Python 的数据经常是结构化的：一段 JSON、一次函数调用、一个小工具类。早期大家只能自己造轮子——if/elif 链、字典派发、functools.singledispatch，三种土办法都有各自的别扭。直到 3.10 的 match/case 才把这套能力收进语言里。
  • elif 其实是「if 的 else 里再嵌一个 if」，语法糖而已。所以 if/elif/else 三者只会执行一支，不可能一次进两个。
⚙️ 底层机制 · 条件怎么变成跳转
  • 缩进是在词法分析阶段就被翻译成 INDENT / DEDENT 记号的，解释器靠它维护一个块栈。所以「缩进是语法」不是风格建议，是字面意义上的语法规则。
  • 整个 if/elif/else 编译成一串条件跳转：编译器把各分支按顺序排好，逐个用 POP_JUMP_IF_FALSE 一类的条件跳转指令判断；哪一支为真就执行那一支并跳过后面的分支，条件全不满足就落到最后的 else。
  • 条件求值后走的是 bool() 语义：有 __bool__ 用它，没有就退回 __len__，两个都没有的 objects恒为真（所以自定义类默认是 truthy）。
  • match（3.10+）编译成一串 MATCH_* 字节码：先做字面量相等性检查，再做类型检查，最后按映射 / 序列 / 类模式拆包；命中一个 case 就直接跳进分支体，不存在「落下去执行下一个 case」这回事。

以上是 CPython 的实现细节，可能随版本变化；语言规范只保证「分支互斥」「块由缩进界定」。

match 看着像 C 的 switch，其实差着四条关键区别：不穿透（命中即止，不用 break）、能解构（序列 / 映射 / 类模式直接拆开）、支持守卫（if 追加条件）、没有「最后一个 case 当默认」的约定（默认分支必须显式写 case _）。

pythonmatch 完整语法
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

def describe(p):
    match p:
        case Point(x=0, y=0):                  # 类模式（关键字匹配）
            return "原点"
        case Point(x=0, y=y):
            return f"在 y 轴上，y={y}"
        case [1, 2, *rest]:                    # 序列模式
            return f"以 1,2 开头，剩下 {rest}"
        case {"type": "point", "pos": (x, y)}: # 映射模式
            return f"字典里的点 {x},{y}"
        case 1 | 2 | 3:                        # 或模式
            return "小整数"
        case str() as s if len(s) > 3:        # 类型模式 + 守卫
            return f"长字符串 {s}"
        case _:                                 # 通配符，必须放最后
            return "其它"

print(describe(Point(0, 0)))   # 输出: 原点
print(describe([1, 2, 3, 4]))   # 输出: 以 1,2 开头，剩下 [3, 4]

🧭 为什么这样设计 · else 不是「出错才执行」
  • for 和 while 都留着：for 适合「有一个可迭代对象，逐个处理」；while 适合「次数不知道，只知道什么时候停」。两条路语言都不替你选。
  • 循环为什么带 else？else 的真实语义是「循环没有被 break 打断」。这样「在一堆数据里找东西，找到就 break，找完没找到走 else」这种搜索模式可以写得很顺，而不需要额外搞一个 found 标志位。
  • 为什么没有 do-while？while True: 加一个 break 完全能表达，而 do-while「至少执行一次」的语义在 Python 里反而别扭（得把条件反过来写在末尾）。
  • 为什么把 break 的作用范围收得这么小？只管最近一层循环，写出来的代码行为一眼可见；代价是想一次跳出两层时，得靠标志位或把循环拆成函数。
⚙️ 底层机制 · 循环怎么转成跳转
  • 整个 while 编译成「求值条件 → 真则执行循环体 → 无条件跳回条件」这一圈回跳指令，条件为假时直接落到循环之后的代码。
  • continue 编译成「跳回条件判断处」，不是跳回循环体开头——所以放在循环体末尾的更新代码会被 continue 跳过，这是死循环的高发点。
  • break 编译成「跳出当前块」的跳转，嵌套循环里只影响最近一层。
  • else 块是循环的「正常路径」：只有循环因条件变假而结束时才执行。break 直接跳过它，continue 只是开始下一轮，不算打断，所以 continue 不会跳过 else。循环一次都没跑（while False:）时，else 照样执行。

以上是 CPython 的实现细节，可能随版本变化；语言规范只保证「条件为真才进循环」「break 跳过 else」这两条行为。

包含起点，不包含终点；步长可以为负。

🧭 为什么这样设计 · 循环头说的是「遍历什么」
  • 为什么不是 C 那种 for (i = 0; i < n; i++)？C 的循环头绑死了「计数器」这一种玩法，遍历数组还得自己写 arr[i]。Python 把「取第几个」从语法里拿掉了，循环头只负责回答「我要遍历什么」——于是同一个 for 能遍历列表、字典、文件行、字符串，甚至生成器。
  • 少写一层下标，就没有 off-by-one：for x in items 里不可能写出 items[i+1] 这种越界。
  • 为什么 range 是惰性的？如果 range(10**9) 真的先造出十亿个整数，光分配内存就要几个 GB。惰性 range 只记住「起点、终点、步长」三个数，要几个给几个。
  • 代价是什么？惰性对象不能随便当列表用：range 不支持加法、不支持 append、和列表比较也不相等。想要真列表，得显式 list(...)。
⚙️ 底层机制 · for 其实是两条字节码
  • 整个 for 循环编译成 GET_ITER + FOR_ITER 两条指令：先 iter(obj) 拿到迭代器，再反复对它 next()，直到它抛出 StopIteration，循环就结束。
  • iter(obj) 调对象的 __iter__()，next(it) 调 __next__()。列表、字典、字符串、文件对象、生成器都实现了这套迭代协议，所以 for 对它们一视同仁。
  • range 是一个 C 实现的惰性对象，内部只存 start / stop / step 三个数，一个元素都不存。所以 range(10**9) 只有几十字节，而 list(range(10**9)) 会直接撑爆内存。
  • len(range(...)) 是用数学公式 ceil((stop-start)/step) 算出来的，O(1) 且不遍历；整数成员判断 3 in range(10**9) 同样是公式。

以上是 CPython 的实现细节，可能随版本变化；语言规范保证的是「range 含起点不含终点、步长决定方向」。

🧭 为什么这样设计

字符串在 Python 里是不可变的：一旦创建就不能改，任何"修改"都返回一个新对象。这不是省事，而是换来三样东西：

  • 可哈希：内容不变 → 哈希值不变 → 能当 dict 的键、能放进 set、能拿来做缓存 key。
  • 可安全共享：内存里同一份字符串可以被多处引用，不存在"改了一处、别处跟着变"的惊吓。
  • 天然线程安全：没有"改到一半"的中间状态，多个线程同时读同一个字符串是安全的。

代价是"改"变贵了：s = s + "x" 每次都要把整个串复制一遍，连续拼 n 次就是 O(n²)。所以工程上要么用 "".join(parts) 一次性拼，要么先别拼、留到最后。

横向对比：Java 备了两套类型来分工——String 不可变、StringBuilder 可变；Python 只保留不可变的 str，想拼就用列表或 io.StringIO。少一种类型，代价是多写一个 join。

⚙️ 底层机制

CPython 里的 str 不是"字符数组"，而是一段紧凑的字符缓冲区：先按最省内存的方式挑一种编码存起来，ASCII 串 1 字节/字符、BMP 内的中文 2 字节/字符（UCS-2）、超出 BMP 的 emoji 4 字节/字符（UCS-4）。这三种形态是同一个对象的不同表示，接口完全一样。

🧭 为什么这样设计

字符串方法这么多，因为字符串是程序里最高频的数据。Python 把工具挂在类型上（s.split() 而不是 split(s)），等于给每个字符串预装了一整个文本处理工具箱；再加上字符串不可变，所有方法都不可能原地改坏你的数据，链式调用才敢写：s.strip().lower().split()。

  • find 与 index 双轨：find 用 -1 当"没找到"的哨兵值，index 直接抛异常。Python 的哲学是"错误不该被静默吞掉"，所以判断存在用 in，想报错才用 index。
  • 为什么补了 removeprefix：3.9 之前大家都在手写 s[len(p):] if s.startswith(p) else s。把反复手抄的惯用法收编成标准方法，是 Python 一贯的做法。
  • 为什么 casefold 和 lower 并存：lower 只做一对一映射，casefold 做完整折叠。做去重键时只有 casefold 才正确。
⚙️ 底层机制

绝大多数 str 方法在 C 层实现（CPython 的 Objects/unicodeobject.c），直接操作内部那段紧凑字符缓冲区，不经过 Python 层循环。

  • join 会先算总长度："".join(parts) 先扫一遍算出结果多长，一次性申请内存再拷贝，比循环 += 快得多。
  • lower 和 casefold 走两套表：lower() 是简单大小写映射（一对一），casefold() 用 Unicode 完整折叠表（"ß" 会折成 "ss"）。
  • strip 的空白范围不同：str.strip() 去掉 Python 认定的空白（含 Unicode），bytes.strip() 只去 ASCII 空白。
  • translate 是查表：str.translate() 拿字典按码点查表，bytes.translate() 用一张 256 字节的表。

以上均为 CPython 实现细节，可能随版本变化。

🧭 为什么这样设计

列表是 Python 的「万能容器」，但它不是随便设计的：list 在底层就是一段会自动扩容的连续数组，元素存的是对象引用。三个设计决定连在一起：

  • 为什么是"连续"？连续内存让按下标取元素是 O(1)（算个偏移就行），也让遍历有很好的 CPU 缓存命中率。代价是中间插入/删除要搬移后面的元素，O(n)。
  • 为什么 list 可变、tuple 不可变？不可变的 tuple 能当 dict 的键、能做常量、能被安全共享；可变的 list 才能装下"边收集边改"的日常数据。两种需求，分成两个类型最省心。
  • 为什么 += 比 + 好？a + b 必须造一个新列表（左边是 list、右边也得是 list）；a += b 走的是原地扩展，b 甚至可以是任何可迭代对象，还省一次拷贝。
  • 为什么 sort() 不返回自己？返回 None 能逼你写清楚"我要的是原地排序还是新列表"，也避免 x = x.sort() 这种把数据变成 None 的错。
⚙️ 底层机制

CPython 的 list 对象里有三样东西：一个指向元素指针数组的引用、当前长度 ob_size、以及已分配容量 allocated。往末尾加元素时如果容量满了，不会"刚刚好"扩容，而是多留一点（大约按 1.125 倍增长并做对齐）。

这就是摊还 O(1)：偶尔一次搬移全部元素的 O(n) 成本，被前面那一串 O(1) 的追加摊平了，平均每个元素只花常数时间。所以"连续 append n 次"是 O(n)，而不是 O(n²)。

🧭 为什么这样设计

四种容器不是"差不多的四种写法"，而是四种不同的问题，所以底层结构也完全不同：

  • tuple 为什么不可变？不可变 ⇒ 哈希稳定 ⇒ 能当 dict 的键、能当 set 的元素、能安全共享。当一条记录的字段本来就不该改时，tuple 就是在替你表达这个意图。
  • set 为什么无序？集合的语义是"在不在"，顺序没有意义。无序换来的是 O(1) 的成员判断和天然去重。
  • dict 为什么从 3.7 起保证插入序？因为"有序映射"这个需求太常见（配置、CSV 行、结构化日志），与其让所有人手写 OrderedDict，不如把 dict 本身变成有序的。
  • 为什么 list / dict 不能当字典的键？哈希值必须在对象的整个生命周期里保持不变，否则放进哈希表之后就再也找不到了。可变容器做不到，所以 Python 直接判它们"不可哈希"。
  • 那要一个能当键的集合怎么办？用 frozenset：不可变 ⇒ 哈希稳定 ⇒ 可以当键、可以放进别的 set。
⚙️ 底层机制

CPython 的 dict 不是"哈希桶 + 链表"，而是开放寻址（open addressing）：表就是一串槽位，用键的哈希值算出起始下标直接往里放，撞了就沿探测序列找下一个空位。不用给每个键额外挂链表指针，内存更省、缓存更友好。

3.11 起又进一步改成紧凑布局：整张表拆成两块——一个只存"entry 下标"的紧凑索引数组（按表大小用 1/2/4/8 字节整数），加一个按插入顺序排好的 entries 数组（每项存 hash / key / value）。查找时先在索引数组里探测拿到下标，再去 entries 里取键值；键的内存是"稀"的，索引则可以"密"地排列。

  • 插入序是语言保证（3.7+ 起所有实现都必须满足），但"entries 按插入顺序排"只是当前实现的排法；3.11 之前 dict 用"墓碑"标记删掉的槽位，新布局不再需要墓碑。
  • 哈希带随机盐：字符串哈希按进程随机种子加盐（PYTHONHASHSEED），两次运行里 dict / set 的遍历顺序可能不同——这正是"别依赖遍历顺序"的原因。
  • set 是同一套哈希表，只是没有 value 那一半；frozenset 会缓存哈希值，因为它不可变。
  • tuple 是定长指针串：元素是对象引用，引用不可改，但里面的 list 照样能改。

以上均为 CPython 实现细节，可能随版本变化。

🧭 为什么这样设计
  • 为什么要有五种参数模型？因为「参数名」本身是会变的。一开始叫 name，重构后改成 username——如果外部一直按位置传参，这次改名就悄悄改掉了调用方的语义。用 / 把参数锁成仅位置，就是在告诉调用者：这个名字我随时会改，你别依赖它。
  • 为什么要有仅关键字？布尔开关参数最容易读错：copy(src, True, False) 没人看得懂。写成 copy(src, overwrite=True, backup=False)，顺序就再也无关紧要。
  • 为什么默认参数在定义时求值？为了让 def f(x=CONST) 里的 CONST 只算一次，函数对象的默认表不会随着调用次数膨胀。代价就是你必须记住：默认参数是一个对象，不是一份拷贝。
  • 为什么需要作用域？函数内部不想污染全局，外部又不该随便改函数的内部状态。LEGB 让「同名不同物」成为可能：局部、闭包、全局、内置各占一层。

import functools

def retry(times=3, *, on_error=None):
    """次数留给位置，回调留给关键字。"""
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    if on_error:
                        on_error(i, e)
            raise RuntimeError("重试次数用尽")
        return wrapper
    return deco

@retry(3, on_error=lambda i, e: print("第", i, "次失败:", e))
def fetch(url):
    return f"ok:{url}"

print(fetch("/api"))     # 输出: ok:/api

🧭 为什么这样设计
  • 为什么函数能当值用？因为函数就是对象：有类型、有属性、能放进字典和列表。装饰器、回调、策略模式都建立在这个前提上。
  • 为什么有闭包？有了「函数是一等公民」，就需要把「环境」一起带走：闭包让内层函数记住外层那几个变量，不必一路当参数传下去。
  • 为什么 @ 只是语法糖？把「包装」写成一行 fn = deco(fn) 就够了——装饰器就是一次普通的函数调用。

🧭 为什么这样设计
  • 为什么 Python 用引用语义而不是值语义？赋值只复制「名字 → 对象」这根绑定，不复制对象本身。大数据、模型对象零拷贝地传来传去，性能好；代价就是「改一个，另一个也变」，这正是拷贝存在的理由。
  • 为什么不可变对象不需要拷贝？int、str、tuple 改不了，复制一份除了浪费内存没有意义。所以 copy.copy("abc") is "abc" 为 True。
  • 为什么要分浅和深两种？浅拷贝只复制最外层容器，快且便宜，适合「里面装的全是不可变对象」；深拷贝递归复制整棵对象树，慢但彻底，适合「里面还有可变对象」。
  • 为什么排序要两个函数？sort() 原地改、返回 None，避免多分配一份列表；sorted() 不动原数据、返回新列表，适合「我要的是排好序的副本」。
⚙️ 底层机制
python引用计数与拷贝
import sys
import copy

a = [1, 2, 3]
b = a
print(id(a) == id(b))          # 输出: True   ← id() 就是对象在内存里的地址
print(sys.getrefcount(a))      # 输出: 3   ← 名字 a、名字 b，再加参数本身

s = "abc"
print(copy.copy(s) is s)       # 输出: True   ← 不可变对象直接返回原对象
t = (1, 2)
print(copy.deepcopy(t) is t)   # 输出: True
  • 每个对象头部都有一个引用计数。对象诞生时计数为 1，每多一个名字指向它就 +1，计数归零的当场销毁——这就是 CPython「大部分对象不需要 GC 就活不下去」的原因。
  • 但引用计数治不了循环引用（a 里放 b、b 里放 a，两边计数都降不到 0）。所以 CPython 额外挂了分代循环 GC：容器类对象进第 0 代，GC 定期扫描，幸存者挪到第 1 代、再到第 2 代，扫描频率逐代降低。
  • copy.copy 走 cls.copy() 或 __copy__ 协议；copy.deepcopy 递归复制并用 memo 字典保证「同一个子对象只复制一次」，遇到不可变对象直接原样返回。
🧩

引用计数的具体布局、GC 各代的阈值与触发时机都是 实现细节，可能随版本变化；但「赋值传引用」「不可变对象共享安全」是语言保证。

import copy

class Report:
    def __init__(self, title, tags):
        self.title = title
        self.tags = tags

    def __copy__(self):
        # 浅拷贝：共享 tags 列表
        return Report(self.title, self.tags)

    def __deepcopy__(self, memo):
        # 深拷贝：连 tags 一起复制
        new = Report(self.title, copy.deepcopy(self.tags, memo))
        memo[id(self)] = new
        return new

r = Report("周报", ["重要"])
r2 = copy.copy(r)
r2.tags.append("紧急")
print(r.tags)         # 输出: ['重要', '紧急']   ← 浅拷贝共享 tags
r3 = copy.deepcopy(r)
r3.tags.append("待办")
print(r.tags)         # 输出: ['重要', '紧急']   ← 深拷贝不动原对象

🧭 为什么这样设计
  • 为什么要有 with？open() 拿的是操作系统文件描述符，是有限资源，漏关就泄漏；with 把「获取 → 使用 → 释放」变成语言结构。
  • 为什么文本模式要谈编码？文件里只有字节，屏幕上是字符。文本模式自动做编码 / 解码 + 换行翻译；二进制模式原样搬运字节（图片、压缩包）。
  • 为什么 pathlib 优于 os.path？os.path.join() 只是纯函数，路径始终是字符串；Path（3.4 起）把路径变成对象：/、.glob、.mkdir(parents=True) 都是方法。
⚙️ 底层机制
pythonopen 返回的三层包装
f = open("demo.txt", "w", encoding="utf-8")

  • open() 返回三层包装：TextIOWrapper（编码 + 换行翻译）→ BufferedWriter（攒批再发）→ FileIO（系统调用）。
  • with 靠上下文管理器协议：__enter__ 返回对象，__exit__ 正常结束或抛异常都会调用；文件对象的 __exit__ 即 close()。
  • buffering：默认 -1 用系统块大小；0 是原始 I/O（仅限二进制模式，文本模式会 ValueError）；1 是行缓冲（仅文本模式有效）。
🧩

包装层级、缓冲区大小和 flush 时机都是 实现细节，可能随版本变化；「with 一定调 __exit__」是语言保证。

with 后面跟一个「上下文管理器」对象，as 后面拿到的是它的 __enter__() 的返回值。

💡

等价于手写 try / finally，但永远不会忘记写 finally——这就是它存在的全部理由。

🧩 自己写一个：两个方法就是全部协议
python自定义上下文管理器
class Timer:
    def __enter__(self):
        print("开始")
        return self          # ← as 后面拿到的就是这个

    def __exit__(self, exc_type, exc, tb):
        print("结束")
        return False         # ← False = 不吞掉异常，照常往外抛

with Timer() as t:
    print("干活中", t)

任何实现了 __enter__ / __exit__ 的对象都能用 with——不需要继承任何基类，这是鸭子类型的典型体现。

🔍

__exit__ 收到三个参数：异常类型、异常对象、traceback；没有异常时三个都是 None。

🧭 为什么这样设计
  • 清理动作必须「一定发生」。try/finally 能做到，但语法重、容易漏。with 把「进入」和「退出」绑成一个对象，退出路径只有一条。
  • 协议只有两个方法。这让 with 能用在任何对象上——文件、锁、数据库连接、计时器，都是同一套写法。
  • 异常要不要被吞，由 __exit__ 的返回值决定。返回 False（或 None）= 继续抛；返回 True = 吞掉。默认应该是「不吞」。
  • 上下文管理不限于资源释放。它本质是「进入一段作用域 / 离开时收尾」，用来做锁、事务、临时改目录、计时都行。
⚙️ 底层机制
  • with 语句编译成 SETUP_WITH / BEFORE_WITH（3.11+ 改名）等字节码，效果等价于把 __exit__ 调用塞进 finally 位置。
  • __exit__ 拿到的异常信息来自 sys.exc_info()；在 __exit__ 里 return True 相当于「异常已被处理」，解释器会继续执行 with 块之后的第一行。
  • contextlib.contextmanager 是用生成器模拟这两个方法：yield 之前的代码当作 __enter__，yield 之后的代码当作 __exit__，yield 的值就是 as 拿到的对象。
  • 因此 @contextmanager 装饰的函数必须恰好 yield 一次；yield 两次或零次都会报 RuntimeError。

🧭 为什么这样设计

Python 把「错误」建模成异常对象而不是返回码：调用方要么处理它，要么它一路冒泡到顶层终止程序。没人能「忘记检查」——漏掉的代价是程序崩溃，而不是被忽略的 -1。

异常之所以分层，是因为「能不能恢复」比「出在哪儿」更重要：except 既能精确到 KeyError，也能一行兜住 Exception。

你自己的类class AppError(Exception)业务语义错误
  • 为什么有 else：把「只可能失败的那一行」放进 try，成功路径放 else，避免保护范围过大。

⚙️ 底层机制：异常对象与 traceback 链

try:
    raise ValueError("原始错误")

    try:
        raise RuntimeError("转换失败")
    except RuntimeError as e2:
        print(e2.__cause__)    # 输出: None
        print(e2.__context__)  # 输出: 原始错误

  • raise X from None → 主动切断上下文；except E as e 在 except 块结束时会自动 del e（PEP 3110），断开异常与 traceback 的引用环。

Python 没有真正的 private，靠命名约定和名称改写实现“别碰我”。

🧭 为什么这样设计

类解决的是「把状态和操作状态的行为打包在一起」：没有类，状态只能在函数之间来回传；有了类，状态有了唯一的归属和一份明确的接口。

但 Python 刻意不做 Java 式的强封装：属性默认公开，靠命名约定表达意图。写起来短，代价是「约定」只能靠人和 linter 守。

  • 为什么 self 要写出来：方法就是普通函数，实例只是第一个参数；显式化之后方法能当普通函数传递，也能 Class.method(obj, ...) 直接调。
  • 为什么还要 property：为了在不改调用方代码（依然是 obj.age）的前提下加校验、加缓存、加只读保护——这是向后兼容的 API 演进。
  • 为什么有 classmethod / staticmethod：classmethod 收 cls，能当工厂方法（内部调 cls(...)）并支持子类覆盖；staticmethod 与类和实例无关，只是类里的工具函数。
  • 为什么有 __slots__：纯 Python 对象自带实例字典，字典是哈希表，很贵；对象上百万时砍掉它能明显省内存。
⚙️ 底层机制：属性查找与名称改写

3非数据描述符（只有 __get__）如 functools.cached_property
4类属性实例没覆盖时的兜底

  • 名称改写发生在编译期：类体里出现 __name 时，编译器生成字节码时就把属性名改写成 _ClassName__name，所以不同类里的同名「私有」属性互不冲突；_name 完全不改写。

🧭 为什么这样设计

这四个词其实是同一条链上的四环：闭包是地基，装饰器是它的典型应用，迭代协议是接口约定，生成器是协议的惰性实现。

  • 为什么用闭包：Python 没有专门的「记住环境」语法，只能靠「内层引用外层变量 + 外层返回内层函数」实现——这也正是装饰器需要的形状。
  • 为什么用装饰器：日志、计时、鉴权、重试、缓存这些「横切关注点」不该散落在业务代码里，包装一层函数，业务代码一行不用改。
  • 为什么是协议而不是基类：只要实现 __iter__ / __next__ 就能被 for 遍历，list、dict、文件、生成器共用同一套 for 写法。
  • 为什么生成器省内存：列表推导式先算完所有元素（O(n)），生成器一次只产出一个（O(1)），所以能处理放不进内存的大文件。

def retry(times=3):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for i in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if i == times - 1:
                        raise
        return wrapper
    return deco

@retry(2)

🧭 为什么这样设计

  • 为什么线程和进程要分开看：GIL 让同一时刻只有一个线程执行字节码，纯 Python 的 CPU 任务开线程没用；I/O 等待时 GIL 释放，线程合适。
  • 为什么还要异步：单线程 + 事件循环能扛住成千上万条连接，内存远小于多线程。
⚙️ 底层机制：引用计数与分代 GC

每个对象头部都带引用计数，归零立刻释放——实时、精确、零停顿。但循环引用（A↔B）让计数降不下来，只能靠分代标记清除兜底。

pythonGC 阈值与 GIL 切换
import gc, sys

print(gc.get_threshold())         # 输出: (700, 10, 10)

  • 触发条件：CPython 统计「分配数 - 回收数」的差值，超阈值就扫描。默认 gc.get_threshold() 是 (700, 10, 10)：第 0 代攒够 700 个扫一次，每 10 次升一代。
  • 分代的直觉：多数对象很快就死了，值得马上扫；活得久的扫起来贵，推迟。
  • __del__ 与循环引用：带 __del__ 的对象进「待终结」队列，由 GC 统一调用终结器（3.4 起），有环也能回收，但要等 GC 跑一轮。

以上为 CPython 实现细节，可能随版本变化。

类型注解
与类型系统

注解是写给人和检查器看的「说明文字」：它不改变运行时行为，却能让一大类错误在写代码时就被抓出来。

📦 是什么：类型注解

类型注解是写在参数、返回值和变量旁边的类型说明，比如 def add(a: int, b: int) -> int。它一句话说清「这里应该放什么」，让读代码的人和静态检查器都不用靠猜。

  • 标在函数上叫函数注解，标在类体里叫变量注解。
  • 全都可以省略：不写注解的代码依然 100% 合法，Python 从不要求你标注。
  • 它不是运行时校验：写 x: int 不会让 x = "abc" 报错。
🧭 为什么这样设计
  • Python 出身动态类型传统：变量不声明类型，一个名字随时能指向不同对象。好处是写得快，代价是错误常常到运行时才炸。
  • 直接做成静态语言会挡住脚本、数据清洗这类场景；纯动态又让 IDE 和重构工具瞎眼。折中方案就是可选注解：要严格就写，不要就完全不写，两边都不吃亏。
  • 核心取舍是注解对运行时零影响：不写不会让程序变慢，写了也不会自动拦下错误参数——那是 pydantic、beartype 这类运行时校验库的活。
  • 和 assert 划清界限：assert 是运行时检查（还能被 python -O 关掉），注解只服务于静态分析。
⚙️ 底层机制

现代 OOP：dataclass、
Enum 与描述符

手写的样板代码让类越来越重；dataclass、Enum、property 和描述符，把「声明」和「行为」彻底分开。

📦 是什么：现代 OOP 三件套
  • dataclass：写字段声明，自动补 __init__ / __repr__ / __eq__。
  • Enum：把「有限的一组取值」变成一等公民，而不是到处传字符串。
  • 描述符：把「属性的存与校验」封装成可复用小类。

共同点：你只描述「是什么」，机械代码交给框架。

🧭 为什么这样设计
  • Python 的类「什么都要自己写」：__init__ / __repr__ / __eq__ 各写一遍，字段一多就是几十行样板。
  • @dataclass 的取舍：用声明换样板。你写「有哪些字段、什么默认值」，它生成方法——逻辑仍然在你手里。
  • 为什么不把注解直接变成运行时类型？那会拖慢所有程序，还让「可选」变成「强制」。所以 dataclass 只借注解收集字段。
  • Enum 存在的理由是防拼写错误：Status.ACTIVE 拼错立刻报错，字符串拼错要等运行时才炸。
  • 描述符解决属性的重复逻辑：校验、懒加载、类型转换，写一次到处复用。

class Positive:
    """把属性限制为正数的描述符。"""
    def __set_name__(self, owner, name):   # 类创建时调用
        self.name = name
    def __get__(self, obj, objtype=None):

            raise ValueError("必须是正数")

📦 是什么：match/case

match / case 是 Python 3.10 引入的结构化模式匹配（PEP 634）。左边是一个待匹配的表达式，右边是一串「模式 + 可选守卫」。

  • 模式可以匹配形状：是元组？是映射？有没有某个键？
  • 模式可以顺手取值：匹配成功就把字段绑定到名字上。
  • 模式可以带守卫：case x if x > 10，条件不满足就往下试下一个 case。
🧭 为什么这样设计
  • Python 一直没有 switch，因为它「只是把一串 if/elif 换个写法」，收益不大。
  • 但真实数据是有形状的：一条命令是 ("move", 3)，一条记录是 {"type": "a", "value": 1}。老写法要「先判类型、再取下标、逐个 if」三步走。
  • match 的设计目标是一次把形状、取值、校验写完：模式本身就是一份可执行的形状说明。
  • 所以它和 C/Java 的 switch 有本质差异：switch 比较的是值，match 比较的是结构，能顺手解构出字段；switch 会穿透、需要 break，match 命中即止、永不穿透，也不需要 break。
  • 代价是要小心「裸名字」：case x 不是「x 等于某值」，而是「捕获任意值到 x」，这是新代码最大的误读点。
⚙️ 底层机制

主题表达式只求值一次，然后按书写顺序逐个 case 往下试：第一个匹配成功的分支立即执行，后面的分支全部跳过，所以既不会「穿透」也不需要 break。捕获是给模式里的名字赋值，赋值会泄漏到外层作用域。类模式靠类的 __match_args__ 找到位置参数，映射模式只要求「含有这些键」。实现上会编译成一串 MATCH_* 字节码。以上属于实现细节，可能随版本变化。

迭代器协议
与惰性计算

for 背后其实是一套协议；搞懂它，你就同时搞懂了生成器、管道和大文件处理。

📦 是什么：三个层次
  • 可迭代对象：能被 for 遍历的东西，列表、字符串、文件都是。它提供 __iter__。
  • 迭代器：能一个一个吐出值并且记住自己走到哪了。它提供 __iter__（返回自己）和 __next__。
  • 迭代协议：iter() 和 next() 背后的约定，以及「吐完了就抛 StopIteration」的结束信号。

一句话：可迭代对象是「有一堆东西」，迭代器是「正在发牌」。

🧭 为什么这样设计
  • 用协议而不是基类，是为了避免强制继承：任何类凑齐方法就能被 for 接受，标准库和第三方库才能自由扩展。
  • 「一个一个吐」而不是「一次全给」，是为了省内存：日志、CSV、爬虫的结果常常比内存大得多。
  • 把 __iter__ 和 __next__ 分开，是因为「可重复遍历的容器」和「一次性的流」是两种东西：列表能被遍历十次，文件句柄只能被读一次。
  • 生成器则是用语法换样板：不用手写 __iter__ / __next__ / StopIteration，一个 yield 就够了。
  • 惰性还有一层好处：无限序列。itertools.count() 能表达「从 10 开始每次加 2 的所有整数」。
⚙️ 底层机制
pythonfor 循环的完整展开
class Trace:
    def __init__(self, items):
        self.items = items
    def __iter__(self):
        print("调用 __iter__")
        return self            # 迭代器的 __iter__ 必须返回自己
    def __next__(self):
        print("调用 __next__")
        if not self.items:
            raise StopIteration
        return self.items.pop(0)

for x in Trace([1, 2]):
    print("body", x)

CPython 里 for 大致等价于：先 iter(对象) 拿到迭代器，再不断 next(迭代器)，直到抛出 StopIteration 就静默结束。生成器则靠挂起栈帧实现：碰到 yield 就把当前栈帧存起来交出结果，下次恢复继续跑。属于实现细节，可能随版本变化。

import itertools

def read_lines(path):
    with open(path, encoding="utf-8") as f:
        yield from f                  # 文件行是惰性的

def clean(lines):
    for line in lines:
        line = line.strip()
        if line and not line.startswith("#"):
            yield line

def stats(path):
    total = 0
    for word in itertools.chain.from_iterable(
        line.split() for line in clean(read_lines(path))
    ):
        total += len(word)
    return total

path = "app.log"
with open(path, "w", encoding="utf-8") as f:
    f.write("# 注释行会被过滤\nhello world\nfoo\n")
print(stats(path))       # 输出: 13   ← 5 + 5 + 3
# 一个 10 GB 的日志流过内存，内存占用却只有一行

collections 家族
与容器选型

标准库早就不满足于 list 和 dict 了——计数、默认值、双端队列、不可变记录，各有专用容器。

📦 是什么：collections 家族

collections 是标准库里的容器工具箱：它们大多继承自内置容器，只是换掉或补上某一项能力，所以用起来几乎没有学习成本。

  • Counter：字典的「会自己数数」版本。
  • defaultdict：字典的「缺键自动造一个」版本。
  • deque：两端都能进出、还带长度上限的队列。
  • namedtuple：带字段名的元组。
  • OrderedDict / ChainMap：有序字典 / 多层字典叠看。
  • collections.abc：Sequence / Mapping / Iterable 等抽象基类，用来写「只关心接口」的代码。
🧭 为什么这样设计
  • 内置容器是通用的，要「计数」「带默认值」「双端」就得自己写样板；collections 把这些高频需求做成了开箱即用的子类。
  • 它们不发明新语义：Counter 仍然是 dict，deque 仍然可以迭代，namedtuple 仍然是 tuple。老代码不用改。
  • defaultdict 的取舍是「用一次 d[k] 换掉三行 if」：代码短了，但也把「这个键本来不存在」这件事藏了起来。
  • deque 存在是因为 list 的头部操作是线性复杂度：list.pop(0) 要把后面所有元素往前挪一格，队列一长就是灾难。
  • collections.abc 则是为了接口编程：函数只声明「我要一个 Mapping」，就能收 dict、OrderedDict、ChainMap 乃至任何第三方映射。
⚙️ 底层机制

  • Counter 与 dict 的边界：它支持 + / - / & / | 运算，但只按非负计数思考——- 之后 0 和负数都不留（3.3 起就是这套语义）。
  • namedtuple 字段固定，加字段就要改所有构造处；需要频繁变动的记录，用 dataclass（3.7+）更合适。
  • typing.NamedTuple 是 collections.namedtuple 的类型标注版（3.6.1+），可以带默认值和注解；纯运行时用 collections.namedtuple 就够。
  • 反向的坑：collections.abc 里的 ABC 用来声明接口，不要拿它做 isinstance 的性能优化——那点开销远大于省下的事。

路径交给 pathlib，数据交给 json / csv / tomllib —— 选对工具，能少写一半 bug。

🧭 为什么这样设计

os.path 是一堆函数：join、splitext、basename……参数顺序各不相同，字符串拼接又容易漏分隔符。pathlib 把「路径」变成对象：用 / 运算符拼接、用 .parent / .stem / .suffix 取属性，一行代码读出来就是一句话的意思。

数据格式各有定位：json 自描述、跨语言互通，但没注释也没日期类型；csv 是表格、能流式读写，但类型全丢；tomllib 专门读 pyproject.toml；pickle 最快，却只配给自己用。

  • 路径：Path("data") / "a.csv"，跨平台不用管分隔符。
  • 选型口诀：接口与配置用 json，表格用 csv，项目配置用 tomllib。
  • 红线：pickle 只能反序列化「自己产生」的数据。

json列表 / 字典 / 标量接口返回、配置、前端通信

⚙️ 底层机制

Path 继承自 PurePath，在 POSIX 上是 PosixPath、Windows 上是 WindowsPath，由 os.name 决定 —— 同一份代码跨平台不用改写。

Path 对象是不可变的：parent、with_suffix() 都返回新对象（和字符串一样），所以可以放心缓存、放进 dict 当键。

路径本身不做规范化：Path("a/../b").parent 仍然是 a/..，真正的解释权在操作系统手里。

open() 文本模式返回的是 TextIOWrapper，底下还有缓冲层和原始字节层；Path.read_text() 就是 open(...).read() 的快捷方式。

json 有 C 加速器，遇到不认识的对象直接抛 TypeError；要支持自定义类型必须传 default=。

正则表达式
与日期时间

正则负责「按形状捞文本」，datetime 负责「把时刻说清楚」——两件事都容易写错。

🧭 为什么这样设计

正则的模型只有三件东西：模式（描述形状）、匹配（在文本里找）、分组（拆开找到的东西）。想清这三层，re 的 API 就只剩几个动词：search / match / fullmatch / findall / finditer / sub / split。

正则是搜索工具，不是解析器。HTML、XML、JSON 这类有嵌套结构的输入，用标准库解析器，别用正则硬啃 —— 正则会回溯，复杂输入能把它拖死。

时间这边，Python 刻意区分 naive（不带时区）和 aware（带时区）：它不猜你的本地时区，逼你说清楚。

  • 先 compile 再用：模块级 re.compile() 编译一次反复用，意图清楚也省去查缓存。
  • 能用字符串方法就别用正则：split、startswith、replace 更快也更直白。
⚙️ 底层机制

re 是 C 实现的：先把模式编译成一串带分支、字符类和量词的指令（编译在私有模块 re._compiler 里；旧的 sre_compile 3.15 已移除），匹配时用递归回溯推进。

字符类 [a-z] 编译期就展开成范围表；量词 * 编译成分支指令 —— 回溯既是它的性能来源，也是风险来源。

datetime 是 C 结构体，存年月日时分秒微秒，外加一个 tzinfo 指针和一个 fold 标志（区分夏令时回拨时重复的那一小时）。

naive 还是 aware，只看 tzinfo 是不是 None。两个 datetime 一比较，Python 直接抛错，不替你猜时区。

实现细节，可能随版本变化。

📐 模式速查：字符类、量词、分组、标志
写法含义
[abc] / [^abc]字符类 / 取反字符类
* + ? {m,n}量词：0 次以上 / 1 次以上 / 可选 / 区间

(?:...)非捕获分组，只分组不捕获

pythoncompile 与标志
import re

PATTERN = re.compile(r"""
    ^(?P<key>\w+)\s*=\s*     # 键
    (?P<val>[^#]+?)          # 值：取反字符类 + 非贪婪
    (?:\s*\#.*)?$             # 非捕获分组：可选注释
""", re.VERBOSE | re.MULTILINE)  # VERBOSE 换行注释，MULTILINE 让 ^ $ 逐行匹配

for m in PATTERN.finditer("name = 鲸鱼 # 别名\nage = 3"):
    print(m.group("key"), "=", m.group("val").strip())
# 输出: name = 鲸鱼
# 输出: age = 3
print(re.findall(r"\bcat\b", "concatenate cat catalog"))
# 输出: ['cat']   ← \b 是词边界；去掉会连 concatenate 一起命中

🧭 为什么这样设计
  • 参数解析、类型校验、帮助文本、错误信息四件事一次做完。手写 sys.argv 切片只会得到字符串，转换和校验全要自己来。
  • 只依赖标准库。argparse 开箱即用；click / typer 虽然更好写，但那是第三方依赖。
  • CLI 工具的「用户体验」一大半在这里。报错信息、默认值、--help 是否清楚，决定了别人愿不愿意用你的工具。
  • 错误必须让程序非零退出。argparse 参数不合法时打印 usage 并 sys.exit(2)，这是 Unix 世界的约定：0 成功，非 0 失败。
⚙️ 底层机制
  • 两阶段：先「定义规则」（add_argument 把每条规则存进 parser._actions），再「消费参数」（parse_args 遍历 sys.argv）。
  • 解析时先按前缀把 sys.argv 切成「选项」和「位置参数」两组，再逐条匹配规则；匹配不上的会进入「未知参数」错误分支。
  • type=int 不是「声明类型」，而是传入一个转换函数：type=lambda s: int(s) * 2 也完全合法。
  • action="store_true" 的实现就是「有这个 flag 就把 dest 设为 True」，所以它不需要默认值，默认就是 False。
⚠️ 陷阱清单
python陷阱1 在库里调用 parse_args 会杀掉宿主3.11+
# 库函数里这样写：任何多余参数都会 SystemExit
def main():
    args = argparse.ArgumentParser().parse_args()   # ← 危险

# 正确做法：把 parser 单独造出来，parse_args 接受 argv 列表
def build_parser():
    p = argparse.ArgumentParser(prog="mytool")
    p.add_argument("--verbose", action="store_true")
    return p

def main(argv=None):
    args = build_parser().parse_args(argv)   # ← argv=None 时才读 sys.argv
    return args

原因：parse_args() 默认读 sys.argv。如果这个函数被别的程序当库调用，宿主进程的命令行参数会跟你的参数表打架，argparse 判定「未知参数」后直接 sys.exit(2)——整个宿主程序被你的库ko掉了。

python陷阱2 位置参数顺序敏感

🧭 为什么这样设计
  • 测试是「用代码描述预期行为」。写完之后每次改动都能立刻验证，回归问题从「上线才发现」变成「跑一下就知道」。
  • 断言失败要能一眼看懂。pytest 会把 assert 重写成能显示实际值 vs 期望值的形式，而不是只说「AssertionError」。
  • 函数式写法比类式省事。unittest 要 class TestX(TestCase) + self + setUp；pytest 一个函数就是一条用例。
  • 测试应该测「行为」而不是「实现」。断言外部看得见的结果（返回值、抛出的异常、写入的文件），而不是内部私有字段——否则重构一次就得重写测试。
⚙️ 底层机制
  • pytest 通过 收集（collect）→ 执行（run）→ 报告（report） 三步工作：先扫目录找 test_*.py，再收集其中的 test_* 函数和 Test* 类，最后汇总结果。
  • 断言之所以能给出详细对比，是 pytest 在导入时用 AST 改写了 assert 语句——它把 assert x == y 拆成中间变量，失败时把两边的值都打出来。
  • pytest.raises 本身是一个上下文管理器：__enter__ 记录当前异常，__exit__ 判断异常类型对不对，对不上就重新抛出去。
  • fixture 是 pytest 的依赖注入机制：声明了 fixture 的测试函数，pytest 会在执行前按参数名把准备好的对象传进来。

🧭 为什么这样设计

虚拟环境隔离的是 site-packages，不是解释器本身：同一解释器，每个项目一份第三方包，A 要 requests==2.28、B 要 requests==2.31 也不打架。

logging 的分层是解耦的经典：Logger 决定「这条消息属于谁」，Handler 决定「写去哪」（控制台 / 文件 / 网络），Formatter 决定「写成什么样」。三者分开，库和应用才能各自配置。

  • 库只管发日志，格式和落地方式全部交给应用。

print 只是开胃菜 —— 真正的调试靠断点与 traceback，真正的性能结论靠测量。

🧭 为什么这样设计

print 调试的硬伤很明确：不能停在出错的那一刻、不能看变量的历史、输出会淹没真正重要的信息、线上根本打不上（没有级别、没有时间戳、没有上下文）。

pdb 是标准库自带的交互式调试器，断点就是一个可执行的语句：程序停在那儿，你可以查看变量、临时改值、单步走、往上翻栈。关键是——它不用改代码。

性能问题更不能靠「感觉」。先测量，再优化：timeit 测一段代码的真实成本，cProfile 找时间花在哪，tracemalloc 找内存涨在哪。三者分工明确，不要混用。

  • 调试用 pdb，breakpoint() 一行就能插断点，PYTHONBREAKPOINT=0 可全局禁用。
  • 性能先测后改，改完再测一次，用数据说话。
⚙️ 底层机制

breakpoint() 会读环境变量 PYTHONBREAKPOINT（默认是 pdb），所以换调试器只要改这个环境变量，不用改源码。

pdb 的单步执行，本质是读取当前帧的源码并逐行执行；b 行号 断点靠在那一行插入特殊指令实现，l 列出的是源码文本，不是变量。

异常在 Python 里是一个对象链：每个异常都带 __cause__（raise ... from 显式指定）、__context__（隐式上下文）和 __traceback__（栈帧链）。traceback.format_exception() 把这条链渲染成文本 —— 所以最下面一行才是真正出错的地方，最上面一行只是「谁调用了它」。

cProfile 是 C 写的确定性追踪：每次函数调用和返回都发事件，精确但开销大；采样分析器则是定时抓栈，开销几乎为零，结论是统计出来的。

并发模型
全景

串行、线程、进程、异步 —— 四个工具箱，先认清 GIL 到底锁了什么，再选对那一个。

🧭 为什么这样设计

并发不等于并行。四个模型解决的是不同问题：串行最简单；线程共享内存、切换便宜，适合 IO 等待；进程真并行、能吃满多核，但内存隔离、跨进程要序列化；异步是单线程协作式切换，IO 密集时最省资源，但写错一行就卡死全场。

Python 的 GIL 常被误解成「Python 不能多线程」。准确说法是：GIL 只锁「执行 Python 字节码」这一件事。线程在等网络、读文件、sleep 时会释放 GIL，所以 IO 密集的多线程依然能重叠；被卡的只是纯 CPU 计算。

标准库把这几件事都收进了 concurrent.futures：ThreadPoolExecutor 和 ProcessPoolExecutor 同一个接口，换个类就换了个模型，迁移成本极低。

  • IO 密集 → 线程池或 asyncio。
  • CPU 密集 → 进程池。
  • 任务太短 → 别并发，调度开销比活儿还多。
⚙️ 底层机制

GIL 是解释器级别的互斥锁，保证同一时刻只有一个线程在执行 Python 字节码。它不是「锁住整个程序」，而是在字节码之间检查并让出；默认每 5 毫秒（sys.setswitchinterval）切换一次。

真正做 IO 的 C 函数（socket 收发、文件读、time.sleep）在阻塞期间会释放 GIL，这正是 IO 密集型任务用线程能提速的原因。

线程共享同一份内存，所以共享可变状态必须加锁：Lock 不可重入、需要重入就用 RLock；Event / Condition 管条件同步；Queue 是线程安全的阻塞队列。

进程之间不共享内存，Queue 和 Pipe 传的对象都要 pickle 序列化一次 —— 这就是进程池传大对象会突然变慢的原因。

asyncio 只有一个线程、一个事件循环；协程里的 await 就是让出点，Task 是被调度的最小单位。

实现细节，可能随版本变化。

import json


class Student:
    """一条学生记录。"""
    def __init__(self, name, score):
        self.name = name
        self.score = score

    def __str__(self):
        return f"{self.name}: {self.score}"

    def to_dict(self):
        return {"name": self.name, "score": self.score}


class ScoreManager:
    """把增删查统计都收进管理器。"""
    def __init__(self, path="scores.json"):
        self.path = Path(path)
        self.students = []

    def add(self, name, score):
        # 非法输入当场拒绝，不让脏数据进来
        if not 0 <= score <= 100:
            raise ValueError(f"分数必须在 0-100 之间，收到 {score}")
        self.students.append(Student(name, score))

    def remove(self, name):
        before = len(self.students)
        self.students = [s for s in self.students if s.name != name]
        return len(self.students) != before

    def find(self, name):
        for s in self.students:
            if s.name == name:
                return s
        return None

    def average(self):
        if not self.students:
            return 0
        return sum(s.score for s in self.students) / len(self.students)

    # json 落地，重启不丢
    def save(self):
        data = [s.to_dict() for s in self.students]
        self.path.write_text(
            json.dumps(data, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )

    def load(self):
        if not self.path.exists():
            return
        try:
            data = json.loads(self.path.read_text(encoding="utf-8"))
        except json.JSONDecodeError:
            return                      # 文件坏了就当空数据，别让程序崩
        self.students = [Student(d["name"], d["score"]) for d in data]

def dedupe(items):
    """保持原顺序去重。"""
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out

print(dedupe([1, 2, 2, 3, 1, 4]))     # [1, 2, 3, 4]

# 不可哈希的（比如 dict）用这个版本
def dedupe_unhashable(items):
    out = []
    for x in items:
        if x not in out:
            out.append(x)
    return out

考察点：set 查询是 O(1)，总体 O(n)；但 set 要求元素可哈希，遇到 dict / list 要退回到 in list 的 O(n²) 版本。

class InsufficientFunds(Exception):
    """余额不足。"""


class BankAccount:
    def __init__(self, owner, balance=0.0):
        if balance < 0:
            raise ValueError("初始余额不能为负")
        self.owner = owner
        self.balance = balance
        self.history = []

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("存款金额必须为正")
        self.balance += amount
        self.history.append(("存入", amount))

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("取款金额必须为正")
        if amount > self.balance:
            raise InsufficientFunds(
                f"余额不足：需要 {amount}，只有 {self.balance}"
            )
        self.balance -= amount
        self.history.append(("取出", amount))

    def __str__(self):
        return f"{self.owner}: {self.balance:.2f}"

try:

except InsufficientFunds as e:
    print("取款失败:", e)   # 取款失败: 余额不足：需要 200，只有 150

import functools
import time


def timed(func):
    """打印函数耗时。"""
    @functools.wraps(func)          # ← 保留原函数的 __name__ / __doc__
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            elapsed = time.perf_counter() - start
            print(f"[{func.__name__}] 耗时 {elapsed:.4f}s")
    return wrapper


@timed
def work(n):
    return sum(range(n))


work(1_000_000)
# [work] 耗时 0.0123s

考察点：@functools.wraps 必须写——否则被装饰函数的 __name__ 变成 "wrapper"；*args, **kwargs 让装饰器通用；time.perf_counter() 才是计时的正确选择（time.time() 会被系统时间调整影响）。

        "\n".join(f"line {i}" for i in range(10000)), encoding="utf-8"
    )

# 用法一：直接遍历
for line in read_lines("huge.log"):
    handle(line)

# 用法二：只要非空行
nonempty = (ln for ln in read_lines("huge.log") if ln.strip())
for ln in nonempty:
    handle(ln)

考察点：yield 让函数变成惰性的——不调用 next() 之前一行都不读；with 保证生成器提前结束时文件也会关闭；line.rstrip("\n") 去掉换行但保留其他空白（比 strip() 更温和）。

📏

文件大到内存放不下时，生成器 + 逐行处理是标准解法；readlines() 会把整个文件读进列表，内存直接爆。

⭐ 综合挑战 ③ asyncio 模拟 5 个并发请求
pythonasync_fetch.py
import asyncio


async def fetch(name, delay):
    await asyncio.sleep(delay)      # 模拟网络等待
    return f"{name} 完成（{delay}s）"


async def main():
    results = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.1),
        fetch("C", 0.2),
        fetch("D", 0.1),
        fetch("E", 0.4),
    )
    for r in results:
        print(r)


asyncio.run(main())
# 全部输出只花 ~0.4s（最慢的那个），而不是 1.1s（串行总和）

考察点：asyncio.gather() 并发执行多个协程；asyncio.sleep() 是让出控制权，不是阻塞；总耗时 = 最慢的那个，不是总和。真实场景把 await 换成真正的网络请求（httpx / aiohttp）即可。

⭐ 综合挑战 ④ 给代码加 logging
pythonwith_logging.py3.8+
import logging

# 基础配置：只做一次，放在程序入口
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s %(name)s | %(message)s",
)

log = logging.getLogger(__name__)     # 每个模块一个 logger


def process(items):
    log.info("开始处理 %d 条数据", len(items))   # ← 用 %s 占位，别用 f-string
    total = 0
    for i, item in enumerate(items):
        try:
            total += item
        except TypeError:
            log.warning("第 %d 条不是数字，已跳过", i)
    log.info("处理完成，合计 %d", total)
    return total


process([1, 2, "x", 4])

考察点：日志用 %s 占位而不是 f-string——参数化写法在日志级别被关掉时根本不会做字符串拼接，省性能；getLogger(__name__) 让每个模块有自己的 logger，方便分级控制。
